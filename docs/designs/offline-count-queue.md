## Problem Statement
Clerks count stock on a phone, line by line (`src/components/count/CountScreen.tsx`). Each line is POSTed to `/api/stocktakes/[id]/lines` as it is entered. In a stockroom dead spot the POST fails and the clerk sees "Not saved: no connection. Retry"; a count they don't retry is lost. Batch-tracked products can't be counted offline at all, because the batch list is fetched per product (`/batches?sku=`) and silently falls back to empty on failure.

The original plan already accepted an offline queue (eng decision D5, task T8, 2026-10-09, `~/.gstack/projects/zubair/zubair-unknown-design-20261009-201818.md`); it was deferred to TODOS.md as P2. This design delivers it.

## What Makes This Cool
A recruiter opens the live demo on a phone and flips a **"Stockroom dead spot"** switch on the count screen. They count a few items: each row gets an amber "Kept on this phone" tag and the badge reads "3 counts waiting for signal". They reload: the counts are still there. They flip the switch off and watch the queue send them one at a time until the badge reads "All counts saved". The demo shows its own resilience with no DevTools.

## Constraints
- Next.js 16 App Router, no new dependencies, no service worker (Background Sync is unsupported on Safari/iOS and Firefox; research file below).
- Saves are idempotent by `lineId` (`commandId`); a resend after re-login returns `COMMAND_ID_REUSED`, which already counts as saved.
- Add/replace lines fold in server `countedAt` order (`src/domain/ledger/stocktake.ts:32`), so send order is correctness, not cosmetics.
- Server rejects lines once the stocktake is not OPEN: 409 `STOCKTAKE_CLOSED` (`src/domain/ledger/write.ts:375`), and rejects lines from any session other than the one that opened it: 409 `STOCKTAKE_BUSY` (`write.ts:376`, `openedBy !== sid`). A re-login creates a new session, and `openStocktake` only lets it take over after 2 h idle (`STALE_MS`, `write.ts:346`).
- Expected stock is evaluated at each line's `countedAt`: current onHand minus movements since (`src/domain/ledger/read.ts:224`, `:260`). So `countedAt` drives variance, not just fold order.
- Research: `~/.claude/research/2026-10-13-offline-count-queue.md` (20 sources).

## Premises (agreed)
1. It's a real gap and an unmet promise (D5/T8).
2. Every count-line save, online or offline, goes through one localStorage FIFO queue with one request in flight; new saves never overtake queued ones.
3. Batch-tracked products are countable offline: batch choices for the branch load with the count page, not per product.
4. No service worker, no new dependency. Queued counts survive reload and tab close and send when the page next loads with signal. Opening the page while offline is out of scope.
5. ~~The server keeps setting `countedAt` (arrival time).~~ **Revised after spec review (user D4):** arrival time is wrong for variance (a count queued at 09:00 that arrives at 10:00 misses a 09:30 sale and shows a false +2 found). The phone records `capturedAt`; the server converts it to server time and clamps it (see Recommended Approach).
6. The dead-spot switch only affects the queue's sends, is clearly labelled as a demo control, and persists across reload in sessionStorage.
7. Submit is disabled while this phone has queued counts. Lines rejected after a submit stay visible ("Stocktake already submitted, show these to your manager"). Cross-phone coordination stays in the "Team stocktakes" P3.
8. ~~Out of scope.~~ **Revised after spec review (user D5):** a re-login makes every queued line fail `STOCKTAKE_BUSY` for up to 2 h, so a per-stocktake resume key is in scope.

## Approaches Considered
- **A: Inline in CountScreen.** Smallest diff, but a ~600-line component with the queue rules testable only through E2E. Not chosen.
- **B: Queue module + hook.** Chosen (below).
- **C: Phone as source of truth with a bulk sync endpoint.** New API and semantics, beyond D5. Ruled out.

## Recommended Approach (B)
- **`src/components/count/countQueue.ts`** (framework-free). Storage is **one localStorage key per item**, `bb-q:<stocktakeId>:<lineId>`, holding `{lineId, sku, batchId?, counted, mode, capturedAt, state: "pending" | "failed", error?}`. Each write touches only its own key, so a tab enqueuing while another removes the head can never overwrite it (no read-modify-write of a shared array). Order = `capturedAt`, then `lineId`. API: `enqueue`, `drain`, `retry(lineId)`, `discard(lineId)`, `snapshot`, subscribe. Drain sends the oldest pending item only and removes its key on 2xx or `COMMAND_ID_REUSED`; it classifies failures:
  - network error, timeout (`AbortSignal.timeout(~8s)`), 5xx, 429 → keep, retry with full-jitter backoff (base ~2 s, cap ~60 s); also retry on `online` and `visibilitychange`.
  - 403 → pause, badge "Sign in to send N counts".
  - 409 `STOCKTAKE_CLOSED` → stop; lines stay with "Stocktake already submitted, show these to your manager".
  - 409 `STOCKTAKE_BUSY` → the session changed (re-login). Call open with the stored resume key (below); on success resume draining; if there is no key or it is refused, stop with "This stocktake is being counted on another device. Your N counts are kept on this phone."
  - other 4xx (validation: `BATCH_REQUIRED`, `BATCH_MISMATCH`, …) → mark that item `failed` with the server message and continue. Because each line carries its own `capturedAt`, sending later lines first does not change fold order on the server, and a retried line keeps its original time.
  - Storage unavailable (private mode / quota) → in-memory queue plus a warning that counts won't survive closing the tab.
  - Multi-tab: one draining tab via `navigator.locks.request("bb-queue:<id>")`; `storage` events keep other tabs' badges current.
- **`useCountQueue` hook**: wraps the module with `useSyncExternalStore`; CountScreen's `save()` becomes `enqueue` plus an optimistic entry, so the "Counted N earlier" add/replace prompt sees queued lines. On load, queued items are merged into `initialEntries` **deduped by `lineId`**: if the server already holds a line (it timed out on the phone but arrived), the server copy wins and the queued key is removed, so nothing is shown or counted twice.
- **Server time for a queued count**: the client sends `capturedAt` in the body and its send time in an `x-sent-at` header (a header, so a resend keeps the same body and the same command fingerprint). The server sets `countedAt = clamp(capturedAt + (serverNow − sentAt), stocktake.openedAt, serverNow)`. This corrects a wrong phone clock, and the clamp means a phone can never stamp a count before the stocktake opened or in the future. **Per-item order guard:** the server never stamps a line earlier than the latest stored line for the same stocktake, SKU and batch: `countedAt = max(clamped, latestCountedAtForItem)`. Per-request latency is added to the skew estimate and differs between requests, so without the guard an add followed quickly by a replace could fold in the wrong order; the queue sends in capture order, so the guard keeps per-item fold order equal to capture order. A failed line retried after newer lines of the same item were sent therefore counts as the latest; its Retry button says so. `openedAt` is the original open time and is never changed by a takeover or resume.
- **Trust decision:** `countedAt` is now partly client-chosen. Each line also stores the server's `receivedAt`, and the manager review flags a line whose `receivedAt − countedAt` exceeds 15 minutes ("counted offline, arrived 1h 5m later") so back-dating is visible. A clerk can already enter any count, so choosing a time within [openedAt, now] adds little power; the audit field and flag make it reviewable. Lines without `capturedAt` keep today's behaviour (`countedAt = now`). Zod validates both as ISO dates.
- **Resume key**: `openStocktake` returns a random 128-bit resume key, stored only as a hash on the stocktake; the phone keeps it in `bb-resume:<stocktakeId>`. Open with a matching key takes the stocktake over at once (updating `openedBy`, `clerkLabel`, `lastActivityAt`) instead of waiting out `STALE_MS`. Another phone without the key still gets `STOCKTAKE_BUSY`. Every successful open, stale takeover or resume issues a new key and replaces the stored hash, so only the latest holder's key is valid (a phone that was offline for 3 h after a stale takeover cannot take the stocktake back). Open-with-key only skips the idle-time rule: it still runs the same clerk role and branch checks as a normal open, and compares the key hash with `timingSafeEqual`. Each queued item also stores the `clerkLabel` that recorded it. Lines sent after a resume are recorded under the new session (`clerkId`). If the label now signed in differs from an item's label, those items are held with "3 counts by Clerk Sam: send them as Clerk Priya?" and only sent after confirmation.
- **Submit rule by queue state**: disabled while any item is pending (sending, waiting, paused on 403, or stopped on BUSY) or `failed`. Each failed line has **Retry** and **Discard** (Discard asks for confirmation, then removes the key), so a permanently invalid line can never block Submit for good. Once nothing is left, the badge reads "All counts saved" and Submit enables. After `STOCKTAKE_CLOSED` there is nothing to submit; the lines stay listed until the clerk taps "Clear", which removes the keys.
- **`SyncBadge`**: one always-rendered `role="status"` region: "All counts saved" / "Sending 3 counts…" / "3 counts waiting for signal" / "Sign in to send 3 counts" / "2 not saved, tap to retry". Queued rows in Recent get a "Waiting" tag; the save notice says "Kept on this phone" instead of "Saved". The disabled Submit shows its reason as visible text.
- **Batch choices offline**: the count page server component loads batch choices for all batch-tracked SKUs at the branch (one query, same rules as `batchChoices` in `src/domain/ledger/read.ts:352`) and passes them as props; the per-product fetch goes away.
- **Dead-spot switch**: a labelled toggle on the count screen that swaps the queue's send function for one that fails like a dropped connection; stored in sessionStorage so it survives the reload demo.
- `beforeunload` warning only while the queue is non-empty.

## Success Criteria
- With the switch on (or Playwright `setOffline`), a clerk can count normal and batch-tracked products; reload keeps every queued line; switching back on sends them all and server totals match an online run (including add-after-replace order).
- A save that times out but reached the server is stored once (idempotent resend).
- Submit is disabled with visible reason while anything is queued; enabled once the badge reads "All counts saved".
- 403, 409 and validation failures behave as listed; no count is ever dropped silently.
- Server: a count captured before a sale but arriving after it gets no false variance; `countedAt` is clamped to [openedAt, now]; a wrong `x-sent-at` skew is corrected; a resume key takes over immediately, a wrong or missing key gets BUSY; after a stale takeover by phone B, phone A's old key gets BUSY; a valid key from another branch's clerk is refused; two lines for one item with uneven latency fold in capture order; `receivedAt` is stored and back-dating over 15 min is flagged on review.
- Vitest covers queue order, success/`COMMAND_ID_REUSED` removal, CLOSED stop, BUSY → resume, 403 pause, failed-line retry/discard, concurrent enqueue during a drain (no lost item), reload dedupe by `lineId`, storage fallback; Playwright covers offline count + reload + drain, and timeout-then-success. Typecheck, lint, `npm test`, prod e2e green.

## Reviewer Concerns

Disposition: CONCERNS_RECORDED

Stop: CONVERGENCE

### R2-1 — feasibility (blocking)

**Problem**

> The skew correction serverNow − sentAt also adds each request's network latency, and that latency differs per request. A line A held in flight for ~5 s (slow mobile link, up to the 8 s timeout) gets countedAt ≈ capA + skew + 5 s, while the next line B on a fast request gets capB + skew + 0.1 s. If the clerk entered an add and then a replace for the same item within those few seconds, B folds before A, which reverses add/replace order. The Constraints say fold order is correctness, so this is a regression of the ordering guarantee R1-2 asked for.

**Remedy**

> Keep the server's per-session order consistent with capture order: for example, compute the clock offset once per drain/session (or from the minimum observed delay) instead of per request, or have the server never stamp a line earlier than an already-stored line from the same session with an earlier capturedAt (tie-break on capturedAt/lineId). Add a test with uneven latency between two lines for the same SKU.

### R2-2 — completeness (blocking)

**Problem**

> Premise 5 used to say the server never trusts a phone clock. Now both capturedAt and x-sent-at come from the client, and countedAt decides which movements are subtracted from expected stock (read.ts:224/:260). A clerk, or anyone using the API, can choose any countedAt within [openedAt, now] and so choose the variance, for example to hide shrinkage around a sale. The clamp limits the range but does not stop this. The document presents the change only as clock correction and does not acknowledge or mitigate the trust shift.

**Remedy**

> State the trust decision explicitly. Store the server arrival time alongside the corrected countedAt for audit, and cap or flag lines whose corrected time is far before arrival (e.g. above a threshold, or older than the last online contact) so a manager can see them on review. Test that the arrival time is recorded and that large back-dating is flagged or rejected.

### R2-3 — completeness (blocking)

**Problem**

> Nothing invalidates or rotates the resume key when another phone legitimately takes over after STALE_MS. Phone A goes offline for 3 h with queued counts and phone B takes over. When A reconnects, its drain hits BUSY, A resumes with its old key and takes the stocktake back from B mid-count; B then gets BUSY and resumes with its own key. The two phones ping-pong and both write into one stocktake, which is exactly what openedBy/BUSY exists to prevent.

**Remedy**

> Specify that every successful open or takeover issues a new key and replaces the stored hash, so only the latest holder's key is valid. Also say whether a resume rotates the key. Test that after a stale takeover by phone B, phone A's old key gets BUSY.

### R2-4 — feasibility (blocking)

**Problem**

> Persisting R1-5. Queued items ({lineId, sku, batchId?, counted, mode, capturedAt, state, error?}) still carry no recording user. The resume path now explicitly sends them under whoever signs in next ('recorded under the new session (clerkId), which matches who is holding the phone'), but lines queued before the re-login were counted by the previous clerk, so on a shared phone or after a 403 sign-in by another clerk they are credited to the wrong person.

**Remedy**

> Store the recording user id with each queued item and specify what happens when the signed-in user differs: hold those items and show who must sign in, or ask for confirmation before sending them under the new user. Test it.

### R2-5 — completeness (blocking)

**Problem**

> The resume key is a bearer secret in localStorage that bypasses the STALE_MS wait. The document does not say whether open-with-key still runs the normal authorization checks (signed-in user's branch and role allowed to count this stocktake). Without that, any account signed in on the device, or anyone who reads the key, can take over the stocktake.

**Remedy**

> State that open-with-key only skips the idle-time rule and still enforces the same branch and role checks as a normal open. Compare the key hash in constant time. Add a test that a user from another branch with a valid key is refused.

### R2-6 — feasibility (minor)

**Problem**

> The correction assumes the phone clock does not change between capture and send. A phone that regains signal often resyncs its clock (NTP or carrier time), and a reboot can also change it, so exactly the queued offline case can be mis-corrected. The clamp limits the damage but does not prevent it.

**Remedy**

> Note this limit, or record a monotonic elapsed time (performance.now within one page life) where it is available, and accept clamping otherwise.

### R2-7 — clarity (minor)

**Problem**

> When the key is missing because of the same device (storage cleared, in-memory fallback mode, or a stocktake opened before this feature shipped), the message 'This stocktake is being counted on another device' is wrong. The SyncBadge state list also has no wording for the BUSY-stopped or CLOSED states.

**Remedy**

> Use separate text when no key is stored (e.g. 'Can't resume this stocktake yet, your N counts are kept; ask a manager or wait'), and add the BUSY and CLOSED badge texts to the SyncBadge list.

### R2-8 — consistency (minor)

**Problem**

> The Constraints say a resend after re-login returns COMMAND_ID_REUSED, but the new BUSY constraint (write.ts:376, openedBy !== sid) suggests a resend from the new session may get BUSY before the idempotency check runs. Which check happens first is not established, and it affects how a timed-out line resent after re-login is classified.

**Remedy**

> Check the order of the idempotency and openedBy checks in write.ts and state it. Make sure resume-then-resend still ends in removal via COMMAND_ID_REUSED.

### R2-9 — clarity (minor)

**Problem**

> The clamp's lower bound is stocktake.openedAt. The document does not say whether a stale takeover or a resume resets openedAt. If it does, lines captured before the takeover would be clamped forward and lose their variance correction.

**Remedy**

> State that openedAt is the original open time and is not changed by a takeover or resume (only openedBy, clerkLabel and lastActivityAt change).

### R2-10 — clarity (minor)

**Problem**

> Persisting R1-8: a persistent 5xx still retries forever under '3 counts waiting for signal', which misleads a clerk who does have signal. 403 is still always treated as an expired session.

**Remedy**

> Add badge wording for repeated server errors after N attempts, and say whether 403 can mean anything other than an expired session.

### R2-11 — completeness (minor)

**Problem**

> Persisting R1-9 in part: 'Clear' now handles closed stocktakes, but items for abandoned stocktakes, or ones whose count page can no longer be opened after close, still stay in localStorage with nowhere to see them.

**Remedy**

> Define where lines for a closed stocktake stay visible if its count page can't be opened, and add age-based cleanup of bb-q:/bb-resume: keys.

### R2-12 — scope (minor)

**Problem**

> Persisting R1-10: the dead-spot switch is still assumed always on in production, and the badge does not mention it when it is on, so a clerk who switches it on by accident sees 'waiting for signal' indefinitely.

**Remedy**

> Show the switch state in the badge when it is on, or limit the switch to the demo deployment.

### R2-13 — clarity (minor)

**Problem**

> Persisting R1-11: Success Criteria still say 'switching back on sends them all', but in What Makes This Cool the switch is turned off to send.

**Remedy**

> Change it to 'switching the dead-spot switch off sends them all'.

### R2-14 — feasibility (minor)

**Problem**

> Persisting R1-12: there is still no payload estimate for loading batch choices for the whole branch, no staleness behaviour during a long count, no dead-spot switch persistence in in-memory fallback mode, and no note that beforeunload is best-effort on iOS.

**Remedy**

> Note the payload size and refresh behaviour, and mark beforeunload as best-effort on iOS.
